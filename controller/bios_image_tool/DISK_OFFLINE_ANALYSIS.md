# Disk BASIC が Disk offline になる原因と修正依頼

## Muse くんへの依頼

添付の `2DD.DSK` を使うと、Disk BASIC までは起動しますが、`FILES` を実行すると
`Disk offline` になります。調査の結果、`driver.asm` の `getb` が D レジスタを
破壊するため、正常な FAT12 ブートセクターを `is_boot` が不正と判定する問題が
見つかりました。

`getb` が DE を保存するように `driver.asm` を修正し、DOS2/DOS1 両方のドライバーを
再生成してください。生成 ROM での再現・確認もお願いします。ROM の手作業による
バイナリパッチではなく、ソースを直してビルドしてください。

## 実機での症状

起動時の Pico ログ:

```text
[DISK] image read failed: sector 0 (9)
[DISK] SD is not FAT12/FAT16 --> offline
[DISK] mode=SD direct ready=0 wprot=0 sectors=30277632
[DISK] mode=image /DSK/2DD.DSK ready=1 wprot=0 sectors=1440
```

その後、Disk BASIC で `FILES` を実行すると `Disk offline` と表示されます。
メニュー操作で SD 直接モード（D キー）にも切り替えていますが、カードは FAT32
なので SD 直接モードの `ready=0` は仕様どおりです。試験時はイメージモードに戻し、
ログで `mode=image ... ready=1` になっていることを確認しています。

`2DD.DSK` は SD カードの `/DSK/2DD.DSK` に置いています。Pico はイメージモードで
`ready=1`、容量 1440 セクターと認識しています。

## DSK のブートセクター

添付されたファイルは 737,280 バイト（1440 × 512）で、セクター 0 の BPB は
次の値です。

| オフセット | 値 | 意味 |
|---|---:|---|
| 0 | `EB FE 90` | `is_boot` が許可するジャンプ形式 |
| 11–12 | `00 02` | 512 bytes/sector |
| 13 | `02` | 2 sectors/cluster |
| 14–15 | `01 00` | 予約セクター数 1 |
| 16 | `02` | FAT 数 2 |
| 17–18 | `70 00` | ルートエントリー数 112 |
| 19–20 | `A0 05` | 総セクター数 1440 |
| 21 | `F9` | メディア記述子 |
| 22–23 | `03 00` | FAT サイズ 3 セクター |

したがって、ドライバーの `is_boot` が要求する構造条件を満たす正常な FAT12
ブートセクターです。ディスクの内容が空、またはセクター 0 が FFh であることが
原因ではありません。

## 原因

`driver.asm` の `getb` はオフセット E のバイトを読みますが、アドレス計算前に
`D=0` を設定し、その値を呼び出し元に復元していません。

```asm
getb:
        push    hl
        ld      d, 0
        add     hl, de
        ld      a, [hl]
        pop     hl
        ret
```

一方、`is_boot` は 16 ビット BPB 値を2回の `getb` 呼び出しで調べています。
最初の（下位）バイトを D に退避し、次の（上位）バイトを読み、`A | D` で値が
ゼロでないことを確認しています。2回目の `getb` が D をゼロにするため、
下位バイトの情報が失われます。

例えば予約セクター数 `00 01` の場合:

1. オフセット 14 の読み出し後、`D=01h` になる。
2. オフセット 15 を読む `getb` が `D=00h` にする。
3. `or a, d` は `00h | 00h` となり、予約セクター数をゼロと誤判定する。
4. `is_boot` が失敗し、媒体検出が Disk offline を返す。

同様に、ルートエントリー数 `0070h` と FAT サイズ `0003h` もゼロと誤判定されます。
そのため、このディスクは MBR ではないのに MBR として扱われ、セクター 0 の
末尾に `55 AA` がないことから媒体検出に失敗します。

## 修正方針

`getb` で DE を保存・復元してください。`getb` の用途では E がオフセットなので、
D の一時的なゼロ化後に呼び出し元の DE を復元すれば、既存の値チェックが意図どおり
動作します。

```asm
getb:
        push    hl
        push    de
        ld      d, 0
        add     hl, de
        ld      a, [hl]
        pop     de
        pop     hl
        ret
```

ソース冒頭の説明および `getb` のコメントにあるレジスタ保存契約
（HL、DE、BC を保存）とも一致させてください。共通ソース `driver.asm` から
生成される DOS2 用（バンク 0）と DOS1 用（バンク 3）の両方に反映してください。

## ビルド時の確認事項

1. `python3 build2.py` でアセンブルと ROM 生成が成功すること。
2. 追加した命令が `space (A_DSKIO - $), 0` までの固定配置領域を越えず、
   各エントリー位置とビルドスクリプトの領域サイズ検査を維持すること。
3. DOS2 用・DOS1 用の双方で `getb` が DE を保持すること。
4. 生成 ROM の DOS2 ドライバーで、実機または openMSX にて媒体検出・`FILES` が
   成功すること。DOS1 用ドライバーも少なくともビルドと配置を確認すること。

## ログ中の `image read failed: sector 0 (9)` について

FatFs の結果コード 9 は `FR_INVALID_OBJECT` です。`disk_emu.c` の `image_access`
は失敗時に `s_image_open=false` として最大1回開き直す実装です。この一行だけでは、
開き直し後もセクター読み出しに失敗したとは限らず、DOS の `Disk offline` の直接原因
とは分けて扱ってください。

今回の DOS 側の失敗は、Pico がイメージを `ready=1` と認識している状態で、ドライバー
が BPB を誤判定して媒体検出に失敗することで説明できます。修正後も FR_INVALID_OBJECT
が繰り返す場合は、FatFs の再マウントと `FIL` のライフサイクルを別件として調査して
ください。
