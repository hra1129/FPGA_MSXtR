### 1. 設計

- **ランナー (cpu_test.asm)**: ROM 先頭 16KB (バンク 0/1) に配置。テストデータを
  page2 (8000h-BFFFh, バンク 2/3) 経由で順次読み出して実行し、結果を画面に表示する。
- **スタブ (stub.asm)**: RAM の C000h に常駐。入力状態をレジスタへ設定して被テスト命令を
  実行し、全レジスタ・裏レジスタ・SP・I・PSG R#0・分岐の行き先を保存する。
  総当たり用の `alu_row`（A と F の全組み合わせを実行し、結果を Fletcher チェックサムにまとめる）も含む。
- **生成器 (make_tests.py)**: stub.bin を Python の Z80 エミュレータ（pip パッケージ `z80`）上で
  実行して期待値を生成する。R800 の期待値は Z80 の結果を補正して作る。
  入力は xorshift16 で生成し、ROM には seed・上書き値・期待値の差分だけを格納する。
- **共通定数 (cpu_test_def.asm)**: アセンブラと Python の両方から読み込む。

### 2. メモリ配置

| アドレス | 用途 |
|---|---|
| C000h- | スタブ |
| C200h-C3FFh | 被テスト命令 (INS=C300h)、分岐先 (TGT=C240h) |
| D000h-D01Fh | メモリウィンドウ（メモリアクセス命令の対象） |
| E000h / E040h / E080h | 入力 / 実測 / 期待の状態ブロック (各 64 バイト) |
| E100h-E2FFh | ランナーのワーク、画面のシャドウ |
| F000h | スタック |

テスト中は page0 を RAM に切り替え、RST ベクタに保存ルーチンへの jp を置く。

## 2026-11-24 cz80 に MEMPTR（WZ）を実装（夜）

実機（cz80）で z80test 移植版を実行したところ、ERR 17。すべて `WZ` 系だった。
- ADD HL/IX/IY,RR、ADC/SBC HL,RR
- IN A,(N)、IN R,(C)、IN (C)、INI、IND
- OUT (N),A、OUT (C),R、OUT (C),0、OUTI、OUTD
- LD (BC/DE),A、LD (NN),A

`Q` は全項目 `=NOQ`、`ZT SCF/CCF` は `=NEC`、`ZT ...->NOP'` は `=OLD`（注記のみで、エラーには数えない）。

### 1. 原因
- cz80（T80 ベース）には MEMPTR の実体がなく、`BIT n,(HL)` の X/Y が常に 0 になっていた。
- 通っていた WZ 項目は、たまたま WZ の bit13/11 が 0 だっただけ。

### 2. 修正（src\cz80\cz80.v）
- `ff_wz` を追加した。命令の実行中にアクセスアドレスや読み出しデータを記録し、次の M1 の T2 で命令ごとの規則に従って WZ を更新する。
  - LD A,(BC/DE/nn)、IN A,(n)、IN r,(C)、OUT (C),r、RLD/RRD：アクセスアドレス + 1
  - LD (BC/DE/nn),A、OUT (n),A：{A, (アドレス + 1) の下位}
  - LD (nn),rr / LD rr,(nn)：nn + 1
  - ADD/ADC/SBC HL,rr：演算前の HL + 1
  - EX (SP),HL：新しい HL
  - JP / CALL（条件不成立を含む）：nn
  - RET / RST / JR / DJNZ（分岐時）、割り込み：分岐先
  - (IX/IY+d)：IX/IY+d
  - CPI/CPD：±1、INI/IND：演算前の BC ±1、OUTI/OUTD：演算後の BC ±1
  - ブロック命令のリピート中：PC + 1
- `BIT n,(HL)` の X/Y を `ff_wz[11]` / `ff_wz[13]` から出すようにした。

### 3. 検証
- `make_rtl_vectors.py` で、命令の実行直後の期待 WZ もベクタに出力するようにした（kosarev モデルを 1 命令ずつ実行し、INI/IND とリピート中の値を補正）。

## 2026-11-25 実機確認と V9968 Stack のメモリ検討（朝）

### 1. 実機確認
- 再合成後の実機で cpu_test.rom を実行し、CPU_TEST が全件 PASS（WZ の NG も 0）になったことを確認した。

### 2. メモリの読み出しレイテンシ（bus_valid を受け付けたエッジ → bus_rdata_en）
- **CPU Stack2 の SerialSRAM（ssram.v、clk = 42.95MHz、clk_serial = 214.77MHz）**
  - シミュレーションで実測した。既存の test001/test002 は現行のポートと合わないため、計測用の tb を別に作成した（リポジトリ外）。
  - 1 バイト読み出し：14clk（約 326ns）。その後 3clk で ready に戻り、繰り返し間隔は約 17clk（約 400ns）。
  - 8 バイトバースト：27clk（約 629ns）。書き込み：受け付けから次の ready まで 12clk。
  - SCLK 約 17 クロック分のシリアル転送で律速されるため、clk を 85.9MHz にしても時間はほぼ同じ（28clk）。
- **VDP Stack2 の SDRAM（ip_sdram_tangnano20k_c.v、85.9MHz、CL=2、BL=1、32bit）**
  - RTL を読んで算出した（シミュレーションでは未確認）。
  - 読み出しレイテンシ 7clk（約 81ns）、周期 8clk。帯域は約 43MB/s（SSRAM の約 17 倍）。
- **結論**：VDP の VRAM には SerialSRAM は帯域不足。SDRAM が妥当。

### 3. TangPrimer25K ＋ 16bit SDRAM（BL=2）にする場合の検討
- **周期**
  - VDP のアクセス枠は 8clk ごとで、`ff_vram_valid` は 1clk パルス。SDRAM の周期を 1clk 延ばすと要求を取りこぼす。
  - tRCD を 3clk から 2clk（23.3ns）に縮めて ACT→READ の NOP を 1 つ減らせば、BL=2 でもレイテンシ 7clk、周期 8clk を維持できる見込み。
- **BL=2 にするときの変更点**
  - モードレジスタを WB=0 にする（現在は WB=1 で、書き込みが 1 ワードだけになる）。
  - 書き込みデータとマスクを 2 ビートに分ける（1 ビート目が下位 16bit、2 ビート目が上位 16bit）。
  - 読み出しデータを 2 回取り込んで 32bit に組み立てる。
  - カラムの最下位ビットを 0 に固定する。
- **外付けにすることによる懸念**
  - 読み出しの取り込みタイミング：PLL で位相を調整できるようにし、IO 制約を書き、等長配線とダンピング抵抗を入れる。
  - ピン数：SDRAM だけで約 39 本必要。
  - GW5A 向けに PLL や HDMI 用シリアライザなどのプリミティブを作り直す必要がある。
  - アドレス幅が 13bit になる（32MB 品の場合）。

### 4. リフレッシュ
- **現状**：`vdp_timing_control_ssg.v` で `ff_half_count == 384`（ドット 326）のときだけ、2 ラインに 1 回（63.7µs に 1 回）リフレッシュしている。64ms あたり約 1000 回で、外付け SDRAM に必要な 8192 回の約 1/8 しかない。
- **必要な回数**：8K 品なら 1 ラインあたり 9 回でよい（JEDEC の規格で、最大 8 回分まで先送りできる範囲に収まる）。4K 品なら 5 回。
- **空いている区間**
  - BG：ドット 0〜260 付近。
  - スプライト情報の取得：ドット 260〜307（最大 16 枚 × 3 ドット）。
  - ドット 308〜340 付近は BG もスプライトも使わないので、リフレッシュに使える。
- **案**
  - ドット 318〜326 に、16clk おきに 9 回リフレッシュ要求を出す（下位 4 ビットが 0 のタイミングは今と同じなので、vdp_vram_interface.v は変更不要）。
  - 読み書きはすべて自動プリチャージ付きなので、リフレッシュ前の PRECHARGE ALL を省略できる。省略すれば 8clk 以内に収まり、b スロット（CPU）を止めずに済む見込み（tRFC は要確認）。
- **注意**：リフレッシュ中でも BG とスプライトの要求は止まらないので、両者が重なると表示用の読み出しが黙って失われる。リフレッシュ区間とスプライトや BG の読み出しタイミングが重ならないように管理する必要がある。

  - ED CB / D3 / DB / E3 / EB / FB は、実機では乗算器が動いて DE:HL が変化するが、結果の規則が分かっていない。このため R800 ではテストしない（Z80 では従来どおり NOP(U) を期待する）。
- 生成結果: Z80 は 2267 テストで変わらず、R800 は 1911 テストになった。cpu_test.rom を再生成した。

## 2026-11-28 FS-A1GT 実機の結果に合わせて修正

FS-A1GT の実機で cpu_test.rom を実行したところ、Z80 で ERR 70、R800 で ERR 5 になり、R800 の 603 件目（IN H,(C)）で停止した。
A1GT をリファレンスとして、テスト側を次のように修正した。

### 1. Z80: ZT SCF / ZT CCF
- 実測 CRC（SCF 9FFB24C1、CCF 7801E897）は、Zilog / NEC / ST のどの版とも一致しなかった。
- X/Y の規則を総当たりで調べた。「Y = F.Y、X = (F or A).X」（直前の命令がフラグを変えない場合）で計算した CRC が、2 件とも一致した。
- この結果を `=TR` の代替 CRC として受け入れるようにした（z80test_port.py）。

### 2. Z80: Q（z80ccf 相当）
- フラグを変える命令の後に CCF するテストは OK、フラグを変えない命令（INC RR、SET / RES、LD、EX、PUSH / POP など）の後は NG。
- Zilog の Q の規則では説明できず、3 入力（Q / F / A）の任意の論理でも一致する規則が見つからなかった。
- 規則を特定できないため、Q のテスト（155 件）を Z80 スイートから外した。

### 3. R800: NEG / RETN のミラー
- ED 4C / 54 / 5C（NEG のミラー）と ED 55 / 5D（RETN のミラー）は、実機では NOP（A / F / SP / PC が入力のまま）。
- make_tests.py で、R800 ではミラーを NOP として期待するようにした（ED 64 / 6C / 74 / 7C、ED 65 / 6D / 75 / 7D も同様）。
- cr800 も同じ動作に修正した（cr800_mcode.v）。

### 4. 生成結果
- Z80 2112 テスト、R800 1911 テスト。
- cr800/test_002: 19640 ベクタ、エラー 0。cr800/test_001: 全項目 PASS。

### 5. 未解決
- R800 の IN H,(C)（603 件目）で停止した原因は不明。直前の IM 2 は OK だった。新しい ROM で再確認する。

## R800 の ED 63 で停止する問題

- 原因: FS-A1GT の R800 は、ED 63（LD (nn),HL の別形）を実行すると停止する。DI / EI どちらでも停止し、割り込みでも復帰しない。
- 診断 ROM（ed_nn_test.asm）で確認した。ED 6B は HL に不定の値が入り、ED 43 / 4B / 53 / 5B / 73 / 7B は正常。
- Grauw「Uncovering the R800」の結果（ED 6B は壊れた命令、ED 82 / 8A / 92 / 9A は 3 バイト）とも一致する。
- make_tests.py / z80test_port.py で、ED 63 / 6B / 82 / 8A / 92 / 9A を R800 スイートから外した（z80test の LD RR,(NN) / LD (NN),RR を含む）。
- cpu_test.asm: R キーを押しながら起動すると、Z80 スイートを飛ばして R800 スイートから始めるようにした。
- 生成結果: Z80 2112 テスト、R800 1903 テスト。
- 同日、ed71c_test（オペランドの出どころ）で、置き換わるのはオペコードだけで、オペランドはメモリから読むことを確認した。
  ただし ed71c_test は 2 周目で止まり、ed71d_test（各 4096 回の繰り返し）で、約 3% は置き換えが起きないことがわかった。
- 結果が一定しないので、OUT (C),0(U) A=xx の 4 項目は削除した（R800 1899 テスト）。
- 実機確認: FS-A1GT と FPGA MSXtR の両方で ALL OK（4011 項目、ERR 0）。
- 訂正（同日）: 停止の原因は、R800 の ED 63 が 6363h に H を書き込み、それが cpu_test.rom（ASCII8K）の
  バンク 0 レジスタに当たってバンクが切り替わったためだった。R800 自体は停止しない（下記）。

## R800 の ED 63 / ED 6B の実機の動作

- 診断 ROM（ed63_test.asm / ed63_body.asm）で、ページ 1 を RAM に切り替えて ED 63 / 6B を実行した（HL / nn / PC / A,BC,DE を変えて 13 ケース）。
- ED 63 nn nn: 4 バイト命令。(nn) には書き込まず、常に 6363h に H を 1 バイト書く。nn・PC・ほかのレジスタには依存しない。HL は変化しない。
- ED 6B nn nn: 4 バイト命令。メモリへの書き込みはなく、HL = EB6Bh になった（入力によらず一定）。H の値は環境によって異なり（EB / ED、Grauw 氏の解析では 6B）、L = 6Bh だけが共通。
- 通常は LD (nn),HL に 22 nn nn を使うため、ED 63 の問題は表面化していなかったと考えられる。
- make_tests.py:
  - ED 6B: R800 では 4 バイトの NOP として実行し、HL = EB6Bh に補正して期待値を作る（F は不変）。最初は H を不変としていたが、A1GT で 16 ベクタすべて H = EBh になったため（2026-11-28 19:16）、EBh に合わせた。
  - ED 63: R800 スイートでは専用テスト（レコード 04、id 0）を出力する。ランナーが RAM 上のルーチンでページ 1 を RAM に切り替え、HL を 6 通りに変えて、6363h = H、6362h / 6364h と (nn) が不変、HL が不変であることを確認する。
- cpu_test.asm: レコード 04（special_test）を追加した。
- DD/FD CB d xx の z≠6 は、R800 では 4 バイトの NOP を期待する（FS-A1GT の実機）。
- 生成結果: Z80 2112 テスト、R800 1899 テスト。
- 実機確認: FS-A1GT と FPGA MSXtR の両方で ALL OK（4011 項目、ERR 0）。z80test の参考表示は、A1GT が SCF / CCF =TR、FPGA が SCF / CCF =NEC と LDIR / LDDR / INIR / INDR->NOP' =OLD だった（どちらも許容している別の CRC への一致で、エラーではない）。
