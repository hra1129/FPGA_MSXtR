# 作業履歴 (cpu_test)

## 2026-11-23 CPU テスト ROM の作成

cz80 / cr800 の全命令について、レジスタとフラグの変化を網羅的に検査する
ASCII8K 512KB メガROM `cpu_test.rom` を作成した。openMSX 上での検証まで完了。
実機 (FPGA MSXtR) での動作確認は未実施。

---

### 1. 設計

- **ランナー (cpu_test.asm)**: ROM 先頭 16KB (バンク 0/1) に配置。テストデータを
  page2 (8000h-BFFFh, バンク 2/3) 経由で順次読み出して実行し、結果を画面に表示する。
- **スタブ (stub.asm)**: RAM の C000h に常駐。入力状態をレジスタへ設定して被テスト命令を
  実行し、全レジスタ・裏レジスタ・SP・I・PSG R#0・分岐の行き先を保存する。
  総当たり用の `alu_row`（A と F の全組み合わせを実行し、結果を Fletcher チェックサムにまとめる）も含む。
- **生成器 (make_tests.py)**: stub.bin を Python の Z80 エミュレータ（pip パッケージ `z80`）上で
  実行して期待値を生成する。R800 の期待値は Z80 の結果を補正して作る。
  入力は xorshift16 で生成し、ROM には seed・上書き値・期待値の差分だけを格納する。
- **共通定数 (cpu_test_def.asm)**: アセンブラと Python の両方から読み込む。

### 2. メモリ配置

| アドレス | 用途 |
|---|---|
| C000h- | スタブ |
| C200h-C3FFh | 被テスト命令 (INS=C300h)、分岐先 (TGT=C240h) |
| D000h-D01Fh | メモリウィンドウ（メモリアクセス命令の対象） |
| E000h / E040h / E080h | 入力 / 実測 / 期待の状態ブロック (各 64 バイト) |
| E100h-E2FFh | ランナーのワーク、画面のシャドウ |
| F000h | スタック |

テスト中は page0 を RAM に切り替え、RST ベクタに保存ルーチンへの jp を置く。

### 3. 作業の経過

1. ZMA の書式、R800 資料 (d4.princess r800op)、openMSX の CPUCore.cc の R800 分岐、
   kosarev z80 の API を調査した。
2. stub.asm / cpu_test_def.asm / make_tests.py / cpu_test.asm を作成した。
   - kosarev の `run()` は END_OF_FRAME で戻るため、ループで回すようにした。
   - ランナーの xrnd と Python の xs_next が一致することを、runner.bin を Python の Z80 上で実行して確認した。
3. build.bat を作成し、ROM を生成した（Z80 1802 項目、R800 1784 項目、計 3586 項目、約 382KB）。
4. openMSX (Panasonic FS-A1GT) で実行して、次の 2 点を修正した。
   - **OUT (C),0**: turbo R の Z80（T9769 内蔵の CMOS 版）は FFh を出力するため、期待値を FFh に変更した。
   - **R800 の DD/FD + HL を使わない命令**: openMSX の R800 では 2 バイトの NOP になり、
     後ろのオペランドは次の命令として実行される。Z80 と同じ「プレフィックス無視」で
     テストしていたため暴走していた。Z80 用と R800 用でテストを分けた。
5. 再検証の結果
   - FS-A1GT: 3586 項目すべて ERR 0（エミュレータの時間で約 5 分）
   - FS-A1WSX (MSX2+): Z80 1802 項目が ERR 0、R800 は「SKIPPED」と表示

### 4. 比較から外しているもの

- R800: X/Y フラグ、CCF と ADD/ADC/SBC HL の H、BIT の S/P、ブロック IN/OUT の S/H/P。
- R800: `OUT (C),0`、`LD R,A`→`LD A,R`、DD/FD CB 30-37 はテストしない。
- Z80: SCF/CCF の X/Y フラグ（Q レジスタに依存するため）。

### 5. 未確認事項（実機確認時の注意）

- FPGA の ASCII8K マッパーで、電源投入時のバンクが 0 である前提にしている。
- PSG R#0 の値を読み戻せる前提でテストに使っている。
- 割り込みは VDP の分だけを止めている。ほかの割り込み源はない前提。
- 命令を RAM に書き換えながら実行するため、cr800 のキャッシュが自己書き換えに
  追従しない場合はエラーとして現れる可能性がある。

- エラーが出た項目について、cz80 / cr800 側の不具合か、テスト側の想定違いかを切り分ける。

## 2026-11-24 実機での初回動作確認（朝）

### 1. FPGA MSXtR（cz80 / cr800）

- ROM は起動し、Z80 のテストは 1802 項目すべて最後まで実行された。
- 結果は `TOT:03586 DONE:01802 ERR:00135`。2 行目は `Z80 01802 ALL NEG` のまま。
- 画面に見えていたエラーは `BIT 7,(IY+d)(U)`（FD CB d 7x）の F 不一致。
  - 例: I:23 E:55 G:75、I:AB E:55 G:7D、I:0C E:54 G:7C、I:C3 E:91 G:B9
  - Y/X（bit5/bit3）など、未定義フラグの差が中心に見える（未解析）。
- **数分待っても R800 のテストに移らず、ハングしている。**
  - R800 の 1 項目めの名前も表示されていないので、Z80 → R800 の切り替え区間
    （`main_r800`: leave_test_map → CHGCPU(81h) → di → enter_test_map →
    stream_open → 1 項目めの表示）のどこかで止まっていると考えられる。
  - Z80 のエラーは数えるだけで次へ進む作りなので、エラー数とハングは別の問題。
  - この経路を完走した確認は、今のところ openMSX の FS-A1GT だけ。

### 2. SX-2（MSX2+、V9968）

- 結果は `TOT:01802 DONE:01802 ERR:00005`、`FINISHED: ERROR FOUND`、`R800 TEST SKIPPED (NOT TURBO R)`。
- 画面に見えていたエラー（5 件のうち 4 件）:
  - `DD:INC DE(U)`  INS:DD 13 F2 0A … C: I:EA E:EA G:EB / E: I:87 E:88 G:87
  - `DD:DEC DE(U)`  INS:DD 1B A2 B1 … C: I:AD E:AD G:AC / E: I:23 E:22 G:23
  - `FD:INC DE(U)`  INS:FD 13 65 0F … C: I:3F E:3F G:40 / E: I:88 E:89 G:88
  - `FD:DEC DE(U)`  INS:FD 1B 03 42 … C: I:10 E:10 G:0F / E: I:1A E:19 G:1A
  - いずれも 4/4 ベクタで NG。DE ではなく C（BC の下位）が増減している。
    openMSX では OK だった項目なので、実機 CPU の挙動か、テスト側（スタブ・ランナー）の
    想定違いかを切り分ける必要がある（未解析）。

## 2026-11-24 cz80 / cr800 / CPU 切り替えの修正（夜）

### 1. 命令の修正（RTL テストベンチで cpu_test と同じベクタを流して確認）

- `make_rtl_vectors.py` で cpu_test のベクタを RTL 用に書き出し、
  `cz80\test_003`、`cr800\test_002` で期待値と比較するようにした。
- cz80（`src\cz80\cz80.v`）の修正内容:
  - DD/FD 付き INC/DEC BC/DE、ブロック I/O のフラグ。
  - LD A,I / LD A,R、IN r,(C)、BIT n,(IX+d) の X/Y フラグ。
  - OUT (C),0 の出力値（FFh）。
- cr800（`src\cr800\cr800.v`、`cr800_mcode.v`）の修正内容:
  - MULUW の判定を ED C3 / ED F3 だけに限定。
  - HL を使わない DD/FD xx を 2 バイトの NOP として扱う。
  - ブロック I/O で C フラグを保持する。
- 結果: cz80 は 5099 ベクタ、cr800 は 19352 ベクタで、いずれもエラー 0。

### 2. R800 切り替え時のハングの原因と修正

- Stack2 トップ全体のシステムテスト `src\test_007` を新規に作成した。
  - BIOS の CHGCPU を使い、SLOT#1 の ASCII8K カートリッジ上で
    Z80 ↔ R800 を 4 往復させる。
  - 各 CPU で、バンク切り替え、LDIR、(IX+d)、page0 RAM、VDP I/O を確認する。
  - 物理カートリッジのモデルと ROM モード（SPI 19h）の両方で実行できる。
- **ハングの原因（cr800_inst.v）**
  - R800 が SLOT#1/#2 からオペコードをフェッチするとき（M1 サイクル）、
    /MREQ を T2 の先頭で High に戻していた。
  - そのため、データをラッチする Tw の終わりには SLTSL が外れていて、
    常に FFh（RST 38h）を読んでいた。
  - BIOS（SLOT#0、ROM キャッシュ経由）は動くが、カートリッジ上のコードを
    R800 で実行すると暴走する。これは cpu_test の症状（R800 の 1 項目めを
    表示する前にハング）と一致する。
  - 修正: /MREQ を /RD と同じタイミング（データのラッチと同じ T3 の立ち上がり）で
    解除するようにした。
- シミュレーション環境の修正（実機には影響しない）:
  - `ssram_test_model.v` が VTI7064 用の手順（35h で Quad モードへ移行、EBh で読み出し、
    21 ビットのアドレス）に対応していなかったので対応させた。
  - test_007 の tb で、カートリッジのバンク選択の式を修正した。
- 結果: test_007 は通常モード・ROM モードのどちらも `RESULT: OK switches=8`。
