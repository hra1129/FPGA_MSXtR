# R800 の非公式命令 ED 63 / ED 6B / ED 71 の動作

FS-A1GT の R800 で、`ED 63 nn nn`（LD (nn),HL の別形）と `ED 6B nn nn`（LD HL,(nn) の別形）を
実行したときの動作をまとめる。Z80 では、どちらも `22 nn nn` / `2A nn nn` と同じ動作をする。

## まとめ

| 命令 | 長さ | (nn) へのアクセス | メモリへの書き込み | レジスタの変化 |
|---|---|---|---|---|
| ED 63 nn nn | 4 バイト | なし | 6363h に H を 1 バイト | なし（HL も不変） |
| ED 6B nn nn | 4 バイト | なし（観測上） | なし | HL = EB6Bh（FS-A1GT、RAM 上で実行） |

- 通常の LD (nn),HL / LD HL,(nn) には 22 / 2A を使うので、この問題はふだんは表面化しない。

## ED 63 nn nn

- 4 バイト命令。次の命令は nn の直後から実行される。
- (nn) / (nn+1) には何も書き込まない。
- **常に 6363h に H を 1 バイト書き込む**。6362h / 6364h は変化しない。
- 書き込み先は、nn・PC（命令を置いた番地）・HL・A / BC / DE のどれにも依存しない。
- HL とほかのレジスタは変化しない。
- 6363h はページ 1 なので、ページ 1 がメガ ROM のカートリッジのときは、その書き込みがバンクレジスタに当たる。
  たとえば ASCII8K ではバンク 0 レジスタ（6000h〜67FFh）に当たり、実行中のコードのバンクが切り替わる。
  当初「ED 63 で R800 が停止する」と見えていたのは、これが原因だった（R800 自体は停止しない）。
- 推測される内部の動作: 2 バイト目のオペコード 63h が、アドレスの上位と下位の両方に入り、
  L → H の順に同じ 6363h へ書いている（結果として H が残る）。外から観測できるのは最後の H だけ。

## ED 6B nn nn

- 4 バイト命令。次の命令は nn の直後から実行される。
- メモリへの書き込みはない。(nn) の内容も HL に反映されない。
- FS-A1GT では、入力の HL・nn に関係なく HL = EB6Bh になった（ed63_test の 13 ケースと、cpu_test の 16 ベクタのすべて。どちらも RAM 上で実行）。
- ROM 上で実行した ed_nn_test では H = EDh に見えたことがあり、Grauw 氏の解析では H = 6Bh となっている。H は実行環境によって変わる可能性がある。cr800 と cpu_test は、リファレンスである FS-A1GT の RAM 上での結果（EB6Bh）に合わせている。
  L にも 2 バイト目のオペコード 6Bh が入っていると考えられる。
- F の変化は未確認。

## 確認方法

- 診断 ROM `ed63_test.rom`（[ed63_test.asm](./ed63_test.asm) + [ed63_body.asm](./ed63_body.asm)）
  - ビルド: `zma ed63_body.asm ed63_body.bin` → `zma ed63_test.asm ed63_test.rom`（16KB にパディングする）。
  - 本体を C000h にコピーし、ページ 1 を RAM に切り替えてから、R800（ROM モード、CHGCPU 81h）で実行する。
  - 4000h〜BFFFh を 5Ah で埋め、(nn) を 3Ch,C3h にしてから、`ED op nnL nnH / jp after` を実行する。
  - HL / nn / 命令を置く番地 / A,BC,DE を変えた 13 ケースについて、実行後の HL、(nn)、
    変化したバイトの数と番地を表示する。
- 診断 ROM `ed_nn_test.rom`（[ed_nn_test.asm](./ed_nn_test.asm)）
  - ED 43〜7B の LD (nn),rr / LD rr,(nn) を Z80 と R800 で実行し、命令長（SP の値）とレジスタ値を表示する。
  - カートリッジ上で実行するため、R800 の ED 63 ではバンクが切り替わる点に注意する。

## 実装とテスト

- cr800（`labo/FPGA_MSXtR_CPU_Stack2_000/src/cr800`）は、外から見える結果を上の動作に合わせている。
  - ED 63: 書き込みアドレスを 6363h に固定し、M4 / M5 で L → H の順に書く（`r800_ed63`）。
  - ED 6B: M3 で終わる 4 バイト命令とし、(nn) は読まずに HL へ EB6Bh を書く（`r800_ed6b_l`）。
  - 専用テスト: `cr800/test_003`。
- cpu_test（R800 スイート）
  - ED 6B: 通常のベクタで、HL = EB6Bh、F は不変を期待する（項目名 `LD HL,(nn)(U)`）。
  - ED 63: 6363h が cpu_test.rom のバンクレジスタに当たるため、専用テスト（レコード 04、id 0）で
    ページ 1 を RAM に切り替えて実行する。HL を 6 通りに変え、6363h = H、6362h / 6364h と (nn) が不変、
    HL が不変であることを確認する（項目名 `LD (nn),HL(U)`）。

## ED 71（OUT (C),0 の別形）

Z80 と互換 CPU の間では動作がまちまち（NMOS は 00h、CMOS は FFh を出力）なので、Z80 スイートではテストしない。
FS-A1GT で調べた結果は次のとおり。

- Z80 モード（A1GT 内蔵の Z80）: 2 バイト命令で、ポート (C) に FFh を出力する（CMOS 型）。F は変化しない。
- R800 モード:
  - **I/O 出力は行わない**（C=A1h で PSG R0 が変化しない）。F・A・BC も変化しない。
  - **ED 71 の直後の 1 バイトは実行されず、代わりに A の値がオペコードとして実行される。**
    ただし毎回ではなく、**約 3%（およそ 30 回に 1 回）は置き換わらず、直後の 1 バイトがそのまま実行される**（後述の ed71d_test）。
    置き換わるのはオペコードの 1 バイトだけで、**オペランドは通常どおりメモリから読む**（PC もその分進む）。
    ed71c_test で確認した（`ED 71 xx` の後ろのバイト列 → 結果）。

    | A | ED 71 の後ろ | 結果 |
    |---|---|---|
    | 21h（LD HL,nn） | 00 01 23 | HL=2301h |
    | 21h（LD HL,nn） | 00 45 67 | HL=6745h |
    | 01h（LD BC,nn） | 00 89 AB | BC=AB89h |
    | 06h（LD B,n） | 00 CD | B=CDh |
    | 3Eh（LD A,n） | 00 EF | A=EFh |
    | CCh（CALL Z,nn、Z=1） | 00 00 D0 | D000h へ分岐、戻り番地 = ED 71 の先頭 + 5 |
    | CDh（CALL nn） | 00 00 D0 | D000h へ分岐、戻り番地 = ED 71 の先頭 + 5 |
    | CCh（CALL Z,nn、Z=0） | 00 00 D0 | 分岐しない、PC は 3 バイト進む |
  - 実際の結果（`ED 71` の後ろに `INC DE`（13h）を 8 個並べて実行）。2 回実行して、結果は同じだった。

    | A | A を命令として見ると | 実行された INC DE の数 | その他の変化 |
    |---|---|---|---|
    | 00h | NOP | 7 | なし |
    | 33h | INC SP | 7 | SP + 1 |
    | CCh | CALL Z,nn（F=00h なので不成立） | 5 | なし（PC は nn の 2 バイト分も進む） |

  - 置き換えが起きる確率（ed71d_test。5 ケースを各 4096 回、直前の待ち時間を 0〜255 ループで変えて 2 周実行）:
    A に置き換わったのが 3939〜3968 回、そのまま実行されたのが 128〜157 回（約 3.1〜3.8%）、それ以外は 0 回。
    確率は A や後ろのバイトによらずほぼ同じだった。リフレッシュなどのタイミングで決まっている可能性がある。
    ed71c_test が 2 周目の A=3Eh（`ED 71 00 EF 00`）で止まったのも、置き換えが起きずに RST 28h（EFh）が実行されたためと考えられる。
  - B と C の値（00A1 / FFA1 / 5AA1 / 0000 / FF00）と F の値は、結果に影響しなかった。
  - 外から見ると、「ED 71 xx」が「A の値を命令として実行し、xx は捨てる」ように見える
    （命令のオペランドは xx の後ろから読む）。
    A の値によっては分岐や書き込みが起こり、しかも結果が一定しないので、実行は危険である。
- 推測: R800 は ED 71 の出力データ（A ではなく 0 のはずの値）をうまく扱えず、
  次のオペコードのフェッチで、メモリの値の代わりに内部バス上の A が取り込まれている可能性がある。
- 診断 ROM:
  - `ed71_test.rom`（[ed71_test.asm](./ed71_test.asm) + [ed71_body.asm](./ed71_body.asm)）: Z80 と R800 で ED 71 / ED 41 / ED 79 を比べる。
  - `ed71b_test.rom`（[ed71b_test.asm](./ed71b_test.asm) + [ed71b_body.asm](./ed71b_body.asm)）: R800 だけで、A・B・C・F を変えた 9 ケースを 2 回実行し、HL / IX / IY / SP も表示する。
  - `ed71c_test.rom`（[ed71c_test.asm](./ed71c_test.asm) + [ed71c_body.asm](./ed71c_body.asm)）: ED 71 の後ろのバイト列を指定して、LD / CALL のオペランドがどこから来るかを調べる。
    CALL の飛び先の候補（D000h、AAAAh、AA00h、D0AAh）に着地記録ルーチンを置き、`ld` に着地点、`rt` に積まれた戻り番地を表示する。
  - `ed71d_test.rom`（[ed71d_test.asm](./ed71d_test.asm) + [ed71d_body.asm](./ed71d_body.asm)）: どちらの解釈でも暴走しないケースを各 4096 回実行し、
    A に置き換わった回数（rep）、そのまま実行された回数（mem）、どちらでもない回数（other）を数える。
  - 表示の `n` は実行された INC DE の数、`pt` は PSG R0（55 のままなら出力なし）。
- cr800: 結果が一定しないため、A への置き換えは再現しない。
  - cr800_mcode.v: ED 71 を `irb` で 00h（NOP）に置き換え、I/O サイクルを出さない 2 バイトの NOP にする。
  - 専用テスト: `cr800/test_003`（ED 71 の後ろの命令がそのまま実行されること、I/O 出力がないこと）。
- cpu_test: Z80 / R800 のどちらのスイートでもテストしない。
